# CodeFusion against TFB's leaders at the end of the first night: one full run of the best build

- **Question:** one consistent run of everything kept, to compare with [the first run](2026-10-21-tfb-baseline.md).
- **Code:** perf/techempower (6d417f3) with perf/data-batched-updates (214fd63), perf/pg-pipelining (11a2d71:
  pipelined read groups, shared bursts, RunsAlone, the writer queue, the job pool and its per-thread cache) and
  perf/http-transport merged locally; `Transport = EventLoop`, two Postgres readers per core, four writers: the
  rig's codefusion-cache build.
- **Machine:** the reduced rig (app c4-highcpu-8, Postgres c4-highcpu-8, wrk n2-highcpu-16); the references are the
  first run's, on the same VMs.
- **Method:** TFB's sequence (`scripts/TechEmpowerRig.cs bench`), one round, 04:30 UTC.

- **Memory and CPU:**
  - No collection in any test; RSS 60 to 138 MB.
  - App VM 81 to 100% busy; Postgres 100% on queries, 70 to 77% on db and updates; wrk 89 to 90% on plaintext and
    json.
  - The allocation gate: [steady](2026-10-21-tfb-gate-steady.md), [traced](2026-10-21-tfb-gate-trace-fortunes.md).
- **Conclusion:**
  - CodeFusion leads db, queries and updates on this rig, and is the fastest .NET entry on every test.
  - Behind the best Rust entry: plaintext by 16%, json by 5% (json moved between 1.20M and 1.24M across runs of the
    same code), fortunes by 15%. The overall leader on plaintext and json is libreactor (C), with wrk at 99 to
    100% for it, so its true margin is larger.
  - What is left is our own code per request, in HTTP (the transport session's: a lock per request in the buffer
    pool, the parser, the connection loop) and in fortunes (the page, the list reader); see BACKLOG.md.
  - This rig is the reduced one (32 vCPUs): Postgres limits the leaders on db, queries and updates, and wrk limits
    the fastest on json and plaintext. The full-size rig is needed to settle those.
